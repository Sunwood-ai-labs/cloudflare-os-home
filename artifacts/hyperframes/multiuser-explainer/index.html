01 / OWNER ACTION

共有リンクを発行

OwnerのShare workspaceを開き、権限をGadget onlyにしてリンクを作成した。

操作

Share → Gadget only → Create link

Workspaceの共有ダイアログで、アプリ利用だけを許可する共有リンクを発行。

確認ポイント: 権限表示が Gadget only になっている。
この画面の意味: まだCollaboratorは参加していない。まず入口を作った段階。step 1 / 5
02 / COLLABORATOR JOIN

別アカウントが参加

新しく作ったCollaboratorアカウントでリンクを開き、同じGadgetの画面に入った。

参加

同じアプリを別ユーザーで開く

OwnerのWorkspace名と、共同ホワイトボードのUIがCollaborator側にも表示された。

確認ポイント: Collaborator側はWorkspace編集ではなく、Gadget利用画面に限定されている。
この画面の意味: OwnerとCollaboratorの2つの認証主体が同じGadgetを見ている。step 2 / 5
03 / COLLABORATOR ACTION

Collaboratorが付箋を追加

2人目のユーザーが、白紙のキャンバスに自分の付箋を追加して本文を入力した。

入力

別アカウントCollaborator：リアルタイム追加

付箋追加と本文入力が、Collaborator側のGadget UIから行われた操作。

確認ポイント: eventsが増え、notesが 6 → 7 になった。
この画面の意味: 2人目が“見るだけ”ではなく、Gadget内の共有データを変更した。step 3 / 5
04 / OWNER OBSERVATION

Ownerへリアルタイム同期

同じ付箋がOwner側にも現れ、右側のpresenceとRecent eventsも更新された。

確認

別ユーザーの変更がOwnerへ届く

サーバー側のGadget状態と購読通知を経由し、両画面が同じ状態へ収束した。

確認値: events 21 / notes 7 / strokes 3 / users 3
この画面の意味: “共同”の核心。別アカウントの書き込みがOwner側で観測できた。step 4 / 5
05 / CLEANUP FINDING

後片付けで見つかった制限

Collaborator削除は成功。一方、share linkのRevokeはUIエラーになり、リンク一覧に残った。

要確認

成功したことと、失敗したことを分けて記録

アクセス削除は確認できたが、Revoke操作は「Failed to load sharing info」を表示。ここは成功扱いにしない。

結論: 共同編集は実証済み。共有リンクの無効化UIは追加検証が必要。
一言でいうとAIがスクショを並べただけではなく、別ユーザーが書いた付箋をOwnerへ同期するGadgetを動かした。
次の実験: 同じ付箋の同時編集、Revoke後の再参加可否、Build権限の確認。step 5 / 5
